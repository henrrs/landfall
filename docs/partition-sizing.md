# Partition sizing

Logical partitions are work units; `max_in_flight` is the maximum number of simultaneous source readers. The planner may create more partitions than connections, executing them in waves.

Estimated Arrow bytes = estimated source rows × observed Arrow bytes/row when a calibration probe succeeds, otherwise a contracted-type width estimate. A large workload asks for at least `ceil(bytes / targetPartitionBytes)` and `ceil(bytes / maximumPartitionBytes)` partitions plus enough for `max_in_flight × desiredWaves`; row count, minimum useful size and `maxLogicalPartitions` cap it. Recent failed or slow partitions can increase the count; short partitions can decrease it. The small-table threshold is `minimumPartitionBytes`. CPU, available memory, platform connection cap and the contract's hard source cap affect simultaneous readers. Memory primarily bounds batch size and concurrent readers; a partition streams through bounded Arrow batches.

The SQL probe reads at most `probeMaxRows` rows (default 256), stops at `probeMaxBytes`, and has a separate timeout. Its observed `RecordBatch.nbytes / rows` is advisory. Existing statistics can be missing or stale; estimates must never change semantic coverage. `serviceLevel.targetDuration` is compared to estimated throughput when calibration or history provides a rate; the plan explains an unlikely target without violating connection caps.
